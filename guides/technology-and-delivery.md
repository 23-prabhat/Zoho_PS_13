# Technology choices, responsibilities and submission contents

This guide explains the actual implementation. A package being installed in the
export environment does not mean it is used by the deployed C++ application.

## Why two languages?

| Choice | Why chosen | Actual responsibility |
|---|---|---|
| C++17 | The problem explicitly requires the OpenVINO GenAI C++ API. Native SDK integration and explicit ownership make conversation, cancellation and profiling behavior inspectable. C++17 supplies the filesystem and language facilities used here. | Runs the application: argument/config validation, model loading, streaming generation, history/context policy, cache settings, device discovery, runtime metrics and native resource sampling. |
| Python 3.14 | The validated Hugging Face/Transformers, Optimum Intel and NNCF preparation stack exposes Python tooling. Python also makes subprocess orchestration, structured evidence and repeatable evaluation straightforward. The exact interpreter/package pins match the tested environment. | Downloads/verifies assets; exports and compresses the model; starts the C++ benchmark child; records metadata; grades saved answers; aggregates results; creates charts, reports, brand exports and verified ZIPs; runs preparation/integration tests. |

Python is not required by the deployed inference process after the model and
native binary are prepared. The launcher is Bash and the running model application
is C++. Python subprocess orchestration is not Python model inference. No measured
C++-versus-Python speedup is claimed: the project did not benchmark that comparison.
The Python stack loads an existing pretrained model for conversion; this project
performs no training or fine-tuning.

## Model preparation and inference stack

| Technology | What it does here | Why it is needed / phase |
|---|---|---|
| Qwen2.5-1.5B-Instruct | Supplies the pretrained instruction model; 1.54B total parameters and a pinned source revision. | Meets the requested 1–3B range and provides a model that the recorded laptop runs locally. It is a model, not a framework. |
| Hugging Face Hub | Downloads the pinned checkpoint and its associated files; Shikai verifies the source hash. | Obtains inspectable upstream assets during connected preparation. It is not a hosted inference dependency. |
| Transformers and Hugging Face Tokenizers | Load the original architecture/configuration/tokenizer through the preparation ecosystem. | Let the exporter interpret the Qwen checkpoint and tokenizer. Not imported by the C++ application. |
| CPU-only PyTorch | Provides the source-model execution/conversion foundation used by the exporter. | Supports conversion without a CUDA preparation stack. No project model training is performed. |
| Optimum / Optimum Intel | Provides the OpenVINO export command and integration between model loading, conversion and compression. | Converts the source checkpoint into local OpenVINO artifacts. |
| NNCF | Supplies the low-bit weight-compression machinery used by Optimum Intel. | Produces the tested INT4/INT8 weight formats. INT4 uses group size 128 and ratio 1.0; AWQ calibration is not enabled. |
| OpenVINO Python bindings | Support the Python conversion/export toolchain. | Preparation-time access to OpenVINO; distinct from the native runtime linked by the final executable. |
| OpenVINO GenAI C++ | LLMPipeline performs generation; SchedulerConfig supplies cache controls; ContinuousBatchingPipeline supplies the separate allocation diagnostic. | Implements the required native GenAI backend and supported generation/cache APIs. |
| OpenVINO Runtime C++ | Compiles and executes the exported network on the selected device. | Performs native model execution and exposes device properties underneath GenAI. |
| OpenVINO Tokenizers | Executes exported tokenizer/detokenizer IR and the native chat-template/token APIs. | Connects local text to model tokens without a Python tokenizer service during inference. |

The pinned export environment also contains torchvision. It is retained alongside
the PyTorch/export dependency stack; Shikai does not implement vision, image
inference or a torchvision-based feature. Other installed dependencies support
upstream tooling. The [62-package inventory](dependency-inventory.csv) lists every
export-lock package, its pin, upstream summary and project usage classification.
It does not present all installed libraries as separately implemented features.

## Build, profiling, testing and delivery tools

| Technology | Purpose and reason |
|---|---|
| GCC/G++ or a compatible C++17 compiler | Compiles the native source. The recorded laptop uses GCC; hosted Ubuntu CI validates its own compiler/toolchain. |
| CMake | Defines source targets, SDK linkage, build presets and test registration reproducibly. |
| Ninja | Executes the build graph generated by the selected CMake presets. |
| CTest | Runs native, CLI, integration, reliability and enforced-offline cases with labels/timeouts. |
| Python unittest | Runs the model-free preparation, grading and publication-boundary regressions without a third-party testing framework. |
| Bash | Sources the matching SDK environment, launches the executable and wraps setup/export/build commands. |
| Linux /proc, process clocks and DRM fdinfo | Measure process CPU time, RSS and available GPU client counters directly in native code. CPU sampling is not implemented with psutil. |
| Linux seccomp / optional network namespace | Enforce the offline test; socket-denial checks run before real generation. Offline flags alone are not the proof. |
| OpenCL ICD loader | Supplies libOpenCL.so.1, which the SDK links even for CPU mode. This loader alone does not require GPU hardware or enable a vendor driver. |
| Optional Intel OpenCL runtime / NVIDIA nvidia-smi | Supports the recorded Intel GPU experiment or optional PID-matched NVIDIA monitoring. Successful RTX model inference is not claimed. |
| Python standard library | argparse/json/csv/pathlib/subprocess/statistics handle orchestration, evidence and aggregation; decimal/re support strict checks; hashlib/zipfile support verification and packaging. Public SVG result plots need neither pandas nor Matplotlib. |
| Git / GitHub Actions / Dependabot | Preserve source history, run hosted model-free CI and propose dependency updates. Hosted CI does not download the model or replace full local inference tests. |
| ReportLab | Lays out the college PDF, tables, headings and original vector logo. Report authoring only. |
| pypdf / pdfrw | Inspect/write PDF metadata/navigation and reuse vector figure pages in the report. Report tooling only. |
| Matplotlib / NumPy | Produce the academic report figures from retained CSV measurements. Local report authoring; separate from the standard-library public plotting script. |
| Pillow / FontTools | Export transparent brand PNGs, inspect/render previews, crop captures and outline lettering. Not model inference dependencies. |
| Poppler (pdftotext / pdftoppm / pdfinfo / pdffonts) | Extract/check report text, render pages and inspect page/font properties for visual quality assurance. |

requirements/export.lock.txt pins the full tested export environment;
requirements/build.lock.txt is the smaller CMake/Ninja build environment.
requirements/analysis.lock.txt needs no external Python packages.
requirements/report.lock.txt covers the optional public legacy PDF-addendum tool;
it is not a complete lock for every local academic-report authoring helper.
Downloaded native SDK libraries have their own checksum-pinned bootstrap and
retained upstream notices.

## What exactly is in the submission ZIP?

Extract the archive and open the PDF at its root. The Shikai/ folder contains
buildable source and supporting evidence; it is not a bundled model installer.

| Archive path | Contents and purpose |
|---|---|
| PRABHAT-JHA_SWFW_5S_13.pdf | Full submission report: student/project table, theory, implementation, setup, measurements, screenshots, citations and limits. |
| Shikai/README.md and CONTRIBUTING.md | Entry instructions, dependencies, normal setup and a model-free build/test route. |
| Shikai/src/ and include/ | C++ implementation, interfaces and embedded terminal brand header. |
| Shikai/CMakeLists.txt and CMakePresets.json | Native build targets and repeatable build/test settings. |
| Shikai/scripts/ | Download, verification, export, build, launch, benchmark, grading, reproduction, brand and packaging tools. |
| Shikai/configs/ and benchmarks/ | Runtime profiles, prompts, expected answers and evaluation rules. |
| Shikai/requirements/ | Pinned preparation/build dependencies and analysis/report dependency notes. |
| Shikai/models/manifests/, models/README.md, models/source/.gitkeep | Source revision, model/tokenizer hashes, export settings and local storage instructions; not weights. |
| Shikai/results/validated-*/ | Reviewed historical CSVs, answers, metadata, verification/reproduction logs and checksum indexes. |
| Shikai/docs/ and guides/ | Reviewed technical documentation, selected public figures, research, feature-purpose explanations and this guide. |
| Shikai/assets/brand/ | SVGs, transparent PNGs, wordmark, ASCII, master geometry and fresh brand/terminal verification records. |
| Shikai/submission-evidence/ | Actual captured-output material, figures and report-review records referenced by the PDF. |
| Shikai/.github/ and repository settings | CI/Dependabot definitions and ignore/formatting rules. |
| Shikai/third_party/ and THIRD_PARTY_NOTICES.md | Retained upstream model/runtime notices and attribution. |
| SUBMISSION_MANIFEST.json | Source commit and each archived file's byte size and SHA-256, identifying the delivered version. |

Weights/checkpoints, exported model XML/BIN/tokenizers, the downloaded SDK, virtual
environments, build binaries, caches, Git metadata, credentials, private selection
PDFs and local report-authoring scripts are excluded. These are either recreated
by documented setup or private local material. The finished PDF is included.
Initial preparation requires downloads; generation is offline after preparation.

The packager checks every entry hash, extracts the ZIP and runs all 43 Python
regressions there. Handoff verification compares every public source file with both
Git HEAD and ZIP bytes. The per-entry manifest is the authoritative exact inventory;
the folder table describes the purpose of those files. Upload this single project
ZIP to SETU. The separate SHIKAI_BRAND_KIT.zip is a convenience download, not a
second required college upload.
